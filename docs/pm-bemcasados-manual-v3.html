🎂01 · produto & catálogo

O que a vitrine vende

Antes de qualquer tabela ou tela, é preciso travar o modelo de produto — é a regra que mais muda o schema, a API e a UI ao mesmo tempo.

Decisão fechada com a cliente: cada combinação de sabor, papel/embalagem e tom de cor é um produto próprio, já cadastrado na vitrine — não é o cliente montando a combinação em três escolhas separadas dentro de uma tela. Ou seja: "Bem-casado tradicional · sabor doce de leite · papel kraft · tom rústico" e "Bem-casado tradicional · sabor doce de leite · papel kraft · tom pastel" são dois registros diferentes na tabela produto, cada um com seu próprio preço, foto e estoque de ficha técnica.

Dois tipos de produto

📦 VITRINE (catálogo)

Produto de prateleira

Tem todos os atributos fixos abaixo, já definidos no cadastro. O cliente escolhe o produto pronto, não monta as partes.

🎨 PERSONALIZADO

Produto exclusivo sob encomenda

Sem sabor/papel/tom fixos no cadastro — a combinação nasce da conversa com a cliente (referências, inspirações, detalhes) e segue para negociação via WhatsApp.

Atributos obrigatórios de um produto de vitrine

💰

Preço unitário

Valor por unidade daquele produto específico — cada combinação tem o seu.

🍬

Sabor

Sabor daquele item (ex.: doce de leite, coco, chocolate). Um por produto — sabores diferentes viram produtos diferentes.

🎁

Papel (embalagem)

Embalagem específica daquele item (ex.: papel kraft, celofane, caixa branca).

🎨

Tom de cor

Referência à tabela tom_cor, cadastrada livremente pela administradora (ver abaixo).

Tons de cor — cadastro livre, não lista fixa: tons como pastel, rústico, florido, vibrante ou qualquer outro que a administradora queira usar não ficam fixos como enum no banco. Eles vivem numa tabela própria (tom_cor) que a administradora cadastra e edita pelo painel, sem depender de deploy ou de mexer no banco. Isso evita reabrir o schema toda vez que surgir um tom novo de doce.
DBML · produto + tom_cor
// tom_cor: cadastro livre pela administradora (CRUD no painel admin).

  foto_url varchar

🔀03 · máquina de status

Fluxograma do status_pedido

Depois que o pedido chega pelo WhatsApp, ele passa a existir como registro no sistema e percorre uma máquina de estados controlada pela administradora.

Caminho principal

💬 SOLICITACAOpedido recebido
⚖️ ANALISE_NEGOCIACAOconversa em andamento
✅ CONFIRMACAOvalor e data fechados
📅 AGENDADOdata_evento_confirmada preenchida
🎂 PRONTOprodução concluída
🚚 ENTREGUEpedido finalizado

Desvio 1 — cancelamento

🚫 CANCELADOpor timeout ou cancelamento manual
Regra: um pedido só pode ser cancelado enquanto está em Solicitação ou em Análise/negociação. A partir do momento em que vira Confirmação, não existe mais cancelamento automático. A contagem do prazo de cancelamento começa quando o pedido entra em Análise/negociação.
PENDÊNCIA Ainda falta decidir um prazo mínimo de cancelamento. Hoje a regra é "cancela em até 5 dias, ou até 2 dias antes do evento — o que vier primeiro". O problema: se o evento for daqui a menos de 2 dias, essa conta dá um prazo zero ou negativo, o que não faz sentido. Esse número mínimo ainda precisa ser combinado com a cliente antes de programar essa parte — por enquanto, é um ponto em aberto conhecido, não um valor definitivo.

Desvio 2 — reabertura

↺ A administradora pode voltar um pedido de CONFIRMACAO para ANALISE_NEGOCIACAO (a negociação recomeça). Não existe caminho de volta a partir de AGENDADO em diante.

Tabela de transições permitidas

DeParaQuem acionaObservação
SOLICITACAOANALISE_NEGOCIACAOAdminInício da negociação.
SOLICITACAOCANCELADOAdmin / automáticoTimeout ou desistência.
ANALISE_NEGOCIACAOCONFIRMACAOAdminValor e data fechados com o cliente.
ANALISE_NEGOCIACAOCANCELADOAdmin / automáticoTimeout a partir da entrada nesse status.
CONFIRMACAOANALISE_NEGOCIACAOAdminReabertura — negociação recomeça.
CONFIRMACAOAGENDADOAdmindata_evento_confirmada passa a ser obrigatória.
AGENDADOPRONTOAdminProdução concluída.
PRONTOENTREGUEAdminFim do ciclo de vida do pedido.
valor_estimado_inicial vs valor_confirmado: são colunas separadas em pedido — a estimativa calculada em "monte sua encomenda" nunca é sobrescrita pelo valor fechado na negociação. Os dois convivem lado a lado, em qualquer estado. Toda transição também é registrada em pedido_status_historico, com quem alterou e o motivo (obrigatório na prática para CANCELADO).

🗄️05 · banco de dados

Modelar antes de implementar

Aqui definimos a estrutura que backend, frontend e dados vão compartilhar — já com o modelo de produto fechado na seção 01.

Escolha: usar dbdiagram.io para desenhar e validar visualmente o relacionamento antes de gerar SQL.
  1. Abra o dbdiagram.io e crie o diagrama pm-bemcasados.
  2. Monte os 4 enums (status_pedido, tipo_movimentacao_estoque, origem_movimentacao_estoque, regiao_fornecedor) e as 13 tabelas: usuario_admin, produto, tom_cor, insumo, ficha_tecnica, fornecedor, fornecedor_insumo, cliente, cliente_login_token, pedido, pedido_status_historico, item_pedido, movimentacao_estoque.
  3. Confira PKs e FKs visualmente — atenção especial ao par mutuamente exclusivo pedido_id / fornecedor_insumo_id em movimentacao_estoque (vira CHECK no SQL, o dbdiagram não modela isso).
  4. Exporte PostgreSQL e salve como data/schema.sql — inclua os CREATE TYPE dos enums e adicione o CHECK manualmente após a exportação.

// LGPD — minimização: sem endereço pessoal do cliente.
// Endereço de entrega/evento vive só em pedido.local_*.
Table cliente {
  id uuid [pk]
  nome varchar
  whatsapp varchar [unique, not null] // identificador de login, mas link de verificação vai por e-mail

  email_verificado_em timestamp // preenchido no 1º clique de magic link bem-sucedido; nulo de novo se email for trocado
  criado_em timestamp
  consentimento_lgpd_em timestamp

// Login passwordless — sem hash de senha armazenado.
Table cliente_login_token {
  id uuid [pk]
  cliente_id uuid [ref: > cliente.id, not null]
  token uuid [unique, not null]
  expira_em timestamp [note: 'curto, ex: 15min']
  usado_em timestamp // nulo até o clique; token de uso único
  criado_em timestamp
}

Table pedido {
  id uuid [pk]
  cliente_id uuid [ref: > cliente.id, not null]
  tipo_evento varchar

  data_evento_solicitada date        // o que o cliente pediu originalmente
  data_evento_confirmada date        // preenchido só quando status vira AGENDADO — nunca nulo nesse status

  local_cep varchar
  local_cidade varchar
  local_bairro varchar
  local_logradouro varchar
  local_numero varchar
  local_complemento varchar

  status status_pedido

  valor_estimado_inicial decimal     // calculado no "monte sua encomenda", nunca sobrescrito
  valor_confirmado decimal           // preenchido na negociação/confirmação — nullable até lá

  consentimento_lgpd boolean

  criado_em timestamp
  atualizado_em timestamp
}

Table pedido_status_historico {
  id uuid [pk]
  pedido_id uuid [ref: > pedido.id, not null]
  status status_pedido
  alterado_por uuid [ref: > usuario_admin.id, note: 'nulo em transições automáticas, ex: cancelamento por timeout']
  motivo text // opcional — obrigatório na prática para CANCELADO
  alterado_em timestamp
}

Table item_pedido {
  id uuid [pk]
  pedido_id uuid [ref: > pedido.id, not null]
  produto_id uuid [ref: > produto.id, not null]
  quantidade int
  personalizacao text
  preco_unitario_registrado decimal // snapshot no momento do pedido — produto.preco_unitario muda com o tempo
}

// Ledger de estoque — toda entrada/saída passa por aqui.
// insumo.quantidade_estoque é a soma materializada, não a fonte da verdade.
// pedido_id e fornecedor_insumo_id são intencionalmente opcionais (mutuamente
// exclusivos, dependendo de origem) — o dbdiagram avisa "deveria ser not null"
// porque não entende esse padrão. Regra real fica no CHECK abaixo:
// CHECK (
//   (origem = 'PRODUCAO_PEDIDO'   AND pedido_id IS NOT NULL AND fornecedor_insumo_id IS NULL) OR
//   (origem = 'COMPRA_FORNECEDOR' AND fornecedor_insumo_id IS NOT NULL AND pedido_id IS NULL) OR
//   (origem = 'AJUSTE_MANUAL'     AND pedido_id IS NULL AND fornecedor_insumo_id IS NULL)
// )
Table movimentacao_estoque {
  id uuid [pk]
  insumo_id uuid [ref: > insumo.id, not null]
  tipo tipo_movimentacao_estoque
  quantidade decimal
  origem origem_movimentacao_estoque
  pedido_id uuid [ref: > pedido.id, note: 'preenchido quando origem = PRODUCAO_PEDIDO']
  fornecedor_insumo_id uuid [ref: > fornecedor_insumo.id, note: 'preenchido quando origem = COMPRA_FORNECEDOR']
  criado_em timestamp
}

Table usuario_admin {
  id uuid [pk]
  nome varchar
  email varchar [unique]
  senha_hash varchar
  criado_em timestamp
}

🔐08 · integração & segurança

Conectar tudo sem abrir brechas

Depois que API e interfaces existem separadamente, conectamos autenticação, rotas protegidas e o acesso passwordless do cliente.

ADMIN

JWT + Spring Security

  • BCrypt para senha.
  • POST /api/auth/login retorna JWT escopo ADMIN.
  • /api/admin/** exige escopo ADMIN (inclui produto e tom_cor).
  • Angular usa AuthGuard.
CLIENTE

JWT passwordless

  • Cadastro gera cliente_login_token (uuid, uso único, expira em ~15min).
  • Token entregue só por e-mail; troca por JWT escopo CLIENTE.
  • /api/cliente/** exige escopo CLIENTE.
  • Angular usa um novo ClienteGuard, separado do AuthGuard.
  • Resposta de "solicitar acesso" é sempre genérica; rate limit por cliente_id e por IP.
REGRA

Validar no backend

  • Produto inativo não aparece.
  • Produto não-personalizado exige sabor/papel/tom.
  • Quantidade influencia estimativa.
  • Pedido segue a máquina de status.
  • Estoque mínimo gera alerta.

Fluxo de acesso do cliente (login sem senha)

📧 Solicitar acessowhatsapp ou e-mail cadastrado
✉️ Link por e-mailtoken de uso único · expira em ~15min
🔑 Sessão JWT · CLIENTEacesso só aos próprios pedidos
Passwordless, não sem WhatsApp: o cliente se identifica por WhatsApp ou e-mail na tela de acesso, mas o link só é entregue por e-mail — automatizar envio pelo WhatsApp Business API fica fora do escopo do MVP. Sem e-mail cadastrado, o cliente pede normalmente, só não consegue logar depois; o acompanhamento nesse caso continua manual, pela conversa de WhatsApp com a administradora.
PENDÊNCIA Recuperação de acesso ainda é 100% manual: se o cliente perder o e-mail cadastrado, a administradora troca o e-mail após confirmar identidade pelo WhatsApp. Não existe (nem está previsto) fluxo de recovery automatizado.
application.properties · ambiente
DB_USER=pm_admin
DB_PASSWORD=<senha_local>
API_URL=http://localhost:8080/api
Dois escopos, dois guards: a administradora (escopo ADMIN, painel completo) e o cliente logado (escopo CLIENTE, só os próprios pedidos, sem senha) usam JWT, mas um AuthGuard único que só checa "token existe" não é suficiente: sem verificar o escopo, um JWT de cliente válido poderia navegar rotas do Angular reservadas ao painel admin. Por isso o ClienteGuard é separado do AuthGuard.

name: CI
on: [push, pull_request]
jobs:
  backend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: 'temurin' }

  frontend:

      - run: cd frontend && npm ci && npm run build
