🔍 Contexto

O problema que motivou o sistema

Uma confeiteira autônoma gerencia tudo manualmente — catálogo, encomendas, estoque e negociação — sem nenhuma ferramenta dedicada.

📋 Pedidos por mensagem

Solicitações chegam pelo WhatsApp de forma desestruturada. Sem histórico organizado, confirmações se perdem e detalhes precisam ser renegociados.

📦 Estoque na memória

Insumos são controlados mentalmente ou em cadernos. Faltam alertas de estoque mínimo e rastreamento de consumo real por pedido.

📊 Sem visibilidade

Não existe indicador de quais produtos são mais pedidos, qual o período de maior demanda nem quanto custa produzir cada encomenda.

Consequência: tempo gasto em coordenação reduz o tempo disponível para produção — e qualquer engano em pedido ou estoque gera prejuízo direto para a cliente.

🔑 Acesso do cliente

Por que não pedir senha pro cliente

Quem faz esse tipo de encomenda não entra no sistema todo dia — e ninguém quer travar numa senha esquecida no meio da correria de fechar um casamento ou uma festa.

😩 O problema

O cliente típico usa o sistema poucas vezes — às vezes uma única vez por evento, com meses de intervalo. Nesse tempo todo, é normal esquecer a senha que cadastrou. E como geralmente está resolvendo tudo em cima da hora, qualquer tela de "esqueci minha senha" vira motivo de desistência — ou de voltar a resolver tudo pelo WhatsApp mesmo.

✅ A solução

Em vez de senha, o cliente informa o WhatsApp ou o e-mail que já usou no pedido, recebe um link por e-mail e clica — pronto, já está vendo o próprio pedido. Não existe senha pra esquecer porque não existe senha. É rápido pra quem está com pressa e simples pra quem só usa o sistema de vez em quando.

🔔 Acompanhamento e prazos

O pedido não pode mais ficar esquecido

Antes, depois que o pedido saía pelo WhatsApp, ele podia sumir no meio da conversa. Agora o próprio sistema cobra prazo e avisa as duas pontas antes que isso aconteça.

😕 O problema

Ter um "status" guardado no sistema não é a mesma coisa que acompanhar o pedido de verdade. Um pedido em negociação podia ficar parado por dias sem ninguém perceber — o cliente não sabia se devia cobrar, e a administradora podia perder aquele pedido de vista no meio de tantas conversas.

💡 A solução

O sistema passa a contar os dias desde a última movimentação de cada pedido. Se ninguém mexer nele, avisos automáticos entram em ação — um pra quem devia dar andamento, outro pra quem está esperando resposta.

🔔 Aviso pra administradora

Com 2 dias sem nenhuma movimentação, ela recebe um aviso pra dar o próximo passo — por exemplo, mover o pedido pra produção.

📩 Aviso pro cliente

Com 3 dias sem movimentação (2 dias antes do prazo mínimo de cancelamento), o cliente recebe um aviso de que o pedido pode ser cancelado se ninguém responder.

🚫 Cancelamento

Se ninguém agir até completar 5 dias parado, o pedido é cancelado automaticamente — regra que já existia, agora com avisos no caminho pra ninguém ser pego de surpresa.

🔒 LGPD

Privacidade por design

O sistema coleta o mínimo necessário — minimização de dados como princípio de arquitetura, não como ajuste posterior.

✅ Coletado no cadastro
  • Nome
  • WhatsApp (identificador único)
  • E-mail (opcional — para magic link)
  • Consentimento LGPD com timestamp
🚫 Não coletado no cadastro
  • CEP ou endereço pessoal
  • Cidade ou bairro de residência
  • Qualquer dado além do contato mínimo
Endereço de entrega/evento é coletado no momento do pedido — não no cadastro. Fica vinculado ao pedido, não ao perfil permanente do cliente.
Por que só o endereço da entrega, e não um endereço fixo no perfil? Porque o endereço muda a cada encomenda — hoje é o salão do casamento, na próxima pode ser a casa da festa de aniversário ou o salão da formatura. Guardar um endereço "fixo" no cadastro do cliente não ajudaria em nada (ficaria desatualizado já na encomenda seguinte) e ainda manteria salvo um dado pessoal sem necessidade real — o oposto do que a LGPD pede.
A validar com a cliente: prazo de retenção de dados após entrega e texto final do aviso de privacidade exibido no sistema.

🏗️ Arquitetura

Camadas e responsabilidades

Arquitetura em camadas com separação clara entre interfaces, API e dados. Segurança por dois escopos JWT independentes.

Interfaces
Angular (web) · Ionic (mobile)

Vitrine pública e jornada de encomenda no mobile. Painel administrativo exclusivo na web.

API · Spring Boot
Camadas Controller → Service → Repository

Regras de negócio centralizadas. Validação de estado no backend — nunca só no front.

Dados
PostgreSQL · Python Analytics

Enums nativos, ledger de estoque e ETL Python para indicadores no dashboard.

🔒 Segurança — dois escopos JWT distintos
Escopo ADMIN — autenticação por senha (BCrypt). Acessa /api/admin/**. Protegido por AuthGuard no Angular.
Escopo CLIENTE — magic link por e-mail, sem senha. Acessa /api/cliente/**. Protegido por ClienteGuard (separado do admin).

🛠️ Stack

Tecnologias e justificativa

Cada escolha é justificada pelo contexto — currículo do semestre, compatibilidade entre camadas e viabilidade de entrega.

☕ Backend — Java 21 + Spring Boot

Ecossistema maduro, Spring Security nativo para JWT, Spring Data JPA para mapeamento relacional. Hibernate com ddl-auto=validate — o banco é a fonte da verdade.

🅰️ Frontend — Angular + TypeScript

Framework estruturado com roteamento, guards e HttpClient. Tipagem compartilhada com os DTOs da API reduz erros de integração.

📱 Mobile — Ionic + Angular

Reaproveitamento de lógica e serviços do Angular. Jornada do cliente no mobile; painel administrativo exclusivo da web.

🐘 Dados — PostgreSQL + Python

Enums nativos, integridade referencial e suporte a CHECK constraints complexas. Python com pandas + SQLAlchemy para ETL e indicadores.

🐳 DevOps — Docker + GitHub Actions

Banco containerizado garante ambiente idêntico para o time. CI valida backend e frontend a cada push.

📐 Modelagem — dbdiagram.io

DBML como artefato versionável. Exportação SQL com os tipos e relacionamentos já mapeados, revisados antes da implementação.

🐘 Banco

Modelagem — decisões importantes

13 tabelas, 4 tipos enum nativos, ledger de estoque. Cada decisão tem fundamento técnico ou legal.

Enums nativos (CREATE TYPE)

status_pedido, tipo_movimentacao_estoque, origem_movimentacao_estoque, regiao_fornecedor — integridade garantida pelo Postgres, não só pela aplicação.

Ledger de estoque

movimentacao_estoque registra toda entrada e saída. insumo.quantidade_estoque é saldo materializado — nunca editado diretamente. Sustenta o "consumo real" no dashboard.

Minimização LGPD

Tabela cliente sem endereço pessoal. Endereço de entrega/evento só em pedido.local_* — dado contextual, não perfil permanente.

Magic link (sem senha)

cliente_login_token: token UUID de uso único com expiração curta. Sem hash de senha armazenado — superfície de ataque menor.

Auditoria: pedido_status_historico registra cada transição de status com responsável e motivo — rastreabilidade completa do ciclo de vida do pedido.

⚠️ Riscos

Pontos de atenção e pendências abertas

Decisões técnicas intencionalmente deixadas em aberto — requerem validação com a cliente antes de implementar.

⏱️ Timeout de cancelamento

Prazo = min(5 dias, data_evento − 2 dias) a partir de ANALISE_NEGOCIACAO. Piso mínimo para eventos com menos de 2 dias não está definido. Não implementar o job de cancelamento automático sem validar esse caso com a cliente.

🗂️ Retenção de dados LGPD

Por quanto tempo manter dados de clientes e pedidos após a entrega? Texto final do aviso de privacidade exibido no sistema. A validar com a cliente — não decidir arbitrariamente.

📧 Fornecedor de e-mail

O magic link depende de um SMTP configurado. Avaliar serviço transacional (Resend, Mailgun, SES) e custo antes de ir para produção.

🔢 Rate limit no magic link

Implementar limitação por cliente_id e por IP para evitar abuso de emissão de tokens. Definir thresholds adequados para o volume esperado.
